# Дашборд — СПОРТ МЕДИА

Единый внутренний дашборд компании. Главная страница — точка входа в разделы,
а не таблица.

```
/                      Дашборд — карточки разделов
 ├── /lockers          Занятость шкафчиков (здесь же правки)
 │    └── /lockers/[id]   карточка клуба
 ├── /overlaps         Пересечения между РК
 └── /managers/[slug]  Дашборды менеджеров

/admin                 Технический раздел
 ├── /admin/import     Импорт: справочник клубов и адресные программы
 ├── /admin/settings   Пользователи, роли, менеджеры
 ├── /admin/log        Журнал изменений
 └── /admin/clubs      Справочник клубов — по прямой ссылке, в меню не выводится
```

**Правки делаются прямо на рабочих экранах.** Администратор и редактор
открывают `/lockers`, нажимают на ячейку и меняют статус там же — переходить
в отдельный раздел не нужно. Тот же экран для пользователя с ролью «Просмотр»
работает только на чтение. `/admin/manage` остался как редирект на `/lockers`.

## Пользователи и доступ

Количество пользователей не ограничено. Роль задаётся на пользователя:

| Роль | Что может |
| --- | --- |
| `admin` | Всё, включая пользователей, клубы и настройки |
| `editor` | Ручные изменения занятости и импорт данных |
| `viewer` | Только просмотр внутренних разделов |

Права проверяются дважды: в интерфейсе и в самой базе через RLS-политики
(`lockers_is_admin()`, `lockers_can_edit()`, `lockers_can_view()`), поэтому
обойти их запросом в обход приложения нельзя.

Пользователя можно привязать к менеджеру — это задел под персональные
представления.

**Как выдать доступ:** Supabase → Authentication → Users → Add user (галочка
Auto Confirm) → затем в приложении `/admin/settings` выдать роль по той же почте.

## Модель данных

```
lockers_managers     менеджеры; к ним привязаны клубы
lockers_clubs        каталог клубов (независим от public.clubs дашборда кампаний)
  ├ manager_id       → lockers_managers.id
  └ dashboard_club_id → public.clubs.id (опционально)

lockers_capacity     вместимость: клуб × раздевалка × поверхность
lockers_occupancy    занятость из АП: клуб × месяц × слот × раздевалка
lockers_overrides    ручные правки — ПРИОРИТЕТ над импортом
lockers_imports      история загрузок
lockers_import_rows  сырые строки для дифф-предпросмотра
lockers_admin_log    журнал действий
lockers_admins       пользователи и роли
```

Интерфейс читает не таблицы напрямую, а SQL-функции:

- `lockers_availability(month, surface)` — сетка занятости с наложенными ручными правками;
- `lockers_month_summary(month, surface)` — сводка по месяцу;
- `lockers_overlaps(month, surface)` — пересечения между РК.

Адрес, город и прочие данные клуба наружу не отдаются: функция возвращает только
то, что нужно интерфейсу.

### Кто что ставит

| Что | Откуда берётся |
| --- | --- |
| **Свободно** | состояние по умолчанию. Раздевалка свободна, пока не сказано иное |
| **Занято** | приходит из импорта адресной программы, руками не ставится |
| **Бронь** | ставит человек, с указанием под какого клиента |
| **Закрыто** | ставит человек, с причиной. Единственный способ закрыть раздевалку |

```
всего     = override.total_override ?? capacity.total_lockers ?? null
занято    = occupancy.occupied ?? 0
свободно  = всего == null ? null : всего − занято − бронь
статус    = closed (если админ закрыл)
          | occupied (если занято по АП)
          | reserved (если стоит бронь)
          | available
```

`всего = null` означает «количество шкафчиков ещё не заведено» — раздевалка
показывается как свободная, но без цифр. Это не то же самое, что «ноль
шкафчиков».

### Конфликт брони и АП

Если на раздевалку стояла бронь и потом пришла занятость из адресной программы,
ячейка подсвечивается жёлтым с восклицательным знаком. Так бывает в двух случаях:
бронь превратилась в эту же кампанию (тогда в панели правки жмём «Это та же
кампания») либо про бронь просто забыли (тогда «Снять бронь»). Молча система
такое не проглатывает.

### Клубы без шкафчиков

У части клубов шкафчиков нет — например, у сети DDX только экраны. Такие клубы
помечены `has_lockers = false`: они участвуют в кампаниях и заявках, но в разделе
занятости не показываются.

## Импорт справочника клубов

`/admin/import` → вкладка «Клубы и менеджеры».

Файл — единственный источник клубов. Колонки: 1 — название клуба, 2 — менеджер,
3 (необязательно) — сеть. Строка заголовка распознаётся и пропускается.

Перед записью выполняются проверки, и **при любой из них импорт останавливается,
не записав ничего**:

- дубликаты названий (с указанием строк);
- потерянные строки — есть менеджер, но нет названия клуба;
- несовпадение с контрольным количеством (по умолчанию **318**, поле редактируется).

После импорта показывается, сколько клубов создано, обновлено, скрыто, сколько
менеджеров заведено и сколько активных клубов стало в системе.

Клубы, которых нет в файле, не удаляются, а помечаются неактивными — история
занятости при этом сохраняется.

## Импорт адресной программы

`/admin/import` → вкладка «Адресная программа».

Смысл колонок АП (проверено на боевом файле):

| Колонка | Куда идёт |
| --- | --- |
| `Фитнес-клуб` | сопоставление с каталогом клубов |
| `Количество` | **вместимость** раздевалки, а не занято |
| `Статус конструкций` | занятость: `Готовы к размещению` / `Занято с … по …` / `Занято до …` |
| `Слот` | 1 или 2 — два рекламных места на дверце шкафчика |
| `Зона расположения (список)` | мужская / женская раздевалка |
| `Тип конструкции` | шкафчики / зеркала в раздевалке |
| `Дата старта РК` | период РК; может содержать список свободных окон |

Колонки ищутся **по названиям заголовков**, а не по буквам: в разных листах одной
и той же АП они съезжают на одну-две позиции. Строка, которую не удалось разобрать,
не роняет импорт, а попадает в предпросмотр с пометкой проблемы.

Ручные правки администратора импорт не перезаписывает — в предпросмотре видно,
сколько правок защищено.

## Дашборды менеджеров

Работают на реальных кампаниях из таблиц `campaigns` / `surfaces` /
`surface_clubs`. Карточка кампании показывает кольцо со счётчиками
одобрено / ждём ответ / не отправлено, раскрытие — таблицу клубов с форматами,
исполнителем и фотоотчётом.

Кампания привязывается к менеджеру **через клубы**: SQL-функция
`lockers_manager_placements(manager_slug, month)` идёт по цепочке
`surface_clubs → public.clubs → lockers_clubs.manager_id`. Если в кампании клубы
двух менеджеров, она видна обоим — но каждый видит внутри только свои клубы.
Расхождения в названиях между базами разруливает таблица `lockers_club_aliases`.

Финансовых показателей в дашборде нет — только состояние согласований.

## Цветовая индикация

| Вид | Условие |
| --- | --- |
| Зелёный | свободно больше 60% |
| Жёлтый | свободно 25–60% |
| Розовый | занято или свободно меньше 25% |
| Фиолетовый | стоит бронь |
| **Сплошной красный с подписью «ЗАКРЫТ»** | раздевалка закрыта |
| Жёлтая рамка с «!» | бронь и АП на одной раздевалке — нужен разбор |

У закрытой раздевалки в карточке клуба показываются только статус и комментарий —
цифры «всего / занято / свободно» скрываются, они там не имеют смысла.

## Установка схемы БД

На новом проекте Supabase выполните `supabase/schema.sql` целиком в SQL Editor —
файл состоит из двух частей и применяется сверху вниз. На текущем проекте схема
уже применена.

> `schema.sql` ссылается на `public.clubs` (таблица дашборда кампаний) в поле
> `dashboard_club_id`. На проекте без этой таблицы удалите эту строку.

## Деплой на Vercel

1. Репозиторий на GitHub.
2. Vercel → Add New → Project → выбрать репозиторий.
3. Environment Variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
4. Deploy.

## Демонстрационные данные

В базе есть выдуманные данные для проверки: вместимость у 20 клубов, занятость
по нескольким кампаниям, закрытые раздевалки с причинами, брони, два конфликта
«бронь + АП» и три настоящих пересечения между РК.

Чтобы всё это убрать:

```sql
-- занятость, брони и вместимость
delete from lockers_occupancy;
delete from lockers_overrides;
delete from lockers_capacity;

-- демо-кампании (они видны и в старом дашборде кампаний)
delete from surface_clubs where surface_id in (
  select s.id from surfaces s join campaigns c on c.id = s.campaign_id where c.source_file = 'demo');
delete from surface_periods where surface_id in (
  select s.id from surfaces s join campaigns c on c.id = s.campaign_id where c.source_file = 'demo');
delete from surfaces where campaign_id in (select id from campaigns where source_file = 'demo');
delete from campaigns where source_file = 'demo';
```

Клубы, менеджеры и связи клуб → сеть при этом остаются — это боевые данные.
