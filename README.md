# Дашборд — СПОРТ МЕДИА

Единый внутренний дашборд компании. Главная страница — вход в разделы, а не таблица.

```
/                      Дашборд — карточки разделов
 ├── /lockers          Шкафчики: клуб → раздевалка → слот → статус
 │    └── /lockers/[id]   карточка клуба (шкафчики и зеркала вместе)
 ├── /mirrors          Зеркала: клуб → раздевалка → статус (слотов нет)
 ├── /overlaps         Пересечения между РК
 └── /managers/[slug]  Дашборды менеджеров

/admin                 Технический раздел
 ├── /admin/settings   Пользователи, роли, менеджеры
 ├── /admin/log        Журнал изменений
 └── /admin/clubs      Справочник клубов — по прямой ссылке, в меню нет
```

Правки делаются прямо на рабочих экранах: нажали на ячейку — поменяли статус.
Отдельного раздела «ручные изменения» нет.

## Единица учёта — слот

Количество шкафчиков не считается вообще. Ни в интерфейсе, ни в базе.
Работа идёт на уровне **клуб → раздевалка → слот → статус**.

| Статус | Что означает |
| --- | --- |
| **Свободно** | нет активной РК, слот доступен |
| **Бронь** | слот зарезервирован, размещение ещё не началось |
| **Занято** | РК размещена, слот используется |
| **Закрыто** | недоступен по техническим причинам (ремонт, работы, ограничение) |

Свободный слот в базе не хранится — это состояние по умолчанию. Строка
появляется, только когда статус отличается от свободного.

Статус — не просто слово: у брони, занятости и закрытия есть уточнение
(«ожидание запуска РК», «ремонт», «клуб снят заказчиком»), оно выбирается
из подсказок или вписывается вручную.

### Зеркала

У зеркал своя логика: **слотов нет**, бронирования по слотам нет. Статус ставится
сразу на раздевалку — мужскую или женскую. Отдельный раздел `/mirrors`, в карточке
клуба зеркала показаны отдельным блоком под шкафчиками.

## Как данные попадают в систему

Адресная программа — входная точка. Ручного импорта в интерфейсе нет: файл
присылается ассистенту, он разбирает его и раскладывает по базе через подключение
к Supabase.

```
АП (.xlsx)
   ↓  разбор: scripts/ap-parser.ts
клубы и сети      → lockers_clubs
слоты и периоды   → lockers_slot_status (source = 'ap')
клиент и период   → lockers_campaigns + lockers_placements
```

Статусы, поставленные руками (`source = 'manual'`), разбор АП не затирает.

Подробности — в `scripts/README.md`.

## Модель данных

```
lockers_managers      менеджеры; к ним привязаны клубы
lockers_clubs         каталог клубов
  ├ manager_id        → lockers_managers.id
  ├ network           сеть из файла; null = одиночный клуб
  └ has_lockers       false у клубов без шкафчиков (DDX — только экраны)

lockers_slot_status   статус по форматам:
  ├ lockers           слот + пол
  ├ mirrors           только пол, слотов нет
  └ screens           ни слота, ни пола — статус на клуб
lockers_campaigns     рекламные кампании дашборда менеджера
lockers_placements    размещения: клуб × формат, статусы, ответственный, фотоотчёт
lockers_club_aliases  расхождения названий с другими базами
lockers_admin_log     журнал действий
lockers_admins        пользователи и роли
```

Функции для интерфейса:

- `lockers_slots(month)` — сетка шкафчиков по слотам;
- `lockers_mirrors(month)` — зеркала по раздевалкам;
- `lockers_month_summary(month, surface)` — сводка;
- `lockers_club_overlaps(month)` — пересечения РК между форматами в клубе;
- `lockers_photo_summary(manager_slug)` — контроль фотоотчётов.

Старый дашборд кампаний (`campaigns`, `surfaces`, `surface_clubs`) живёт отдельно
и не изменяется — у него свои таблицы.

## Пересечения между РК

Раздел отвечает на один вопрос: **в каких клубах одновременно идут разные РК
по разным форматам** — стикеры в шкафах, зеркала, экраны.

Строка — клуб, три колонки — форматы, в каждой перечислены кампании этого месяца.
Пересечение = задействовано больше одного формата и больше одной кампании.
Что происходит внутри раздевалки по слотам, видно в разделе «Шкафчики» — там своя
структура, здесь она не дублируется.

| Формат | Единица | Пол |
| --- | --- | --- |
| Стикеры в шкафах | слот 1 / слот 2 | мужская / женская |
| Зеркала | раздевалка | мужская / женская |
| Экраны | клуб | нет |

Фильтры: поиск, менеджер, «есть такой-то формат», «только пересечения / все клубы
с РК». Счётчики сверху — клубов с пересечением, клубов со всеми тремя форматами,
клубов с размещениями, кампаний в работе.

## Дашборд менеджера

Демонстрационный: выдуманные кампании на реальном списке клубов. Живые кампании
компании остаются в старом дашборде и сюда не попадают.

Сверху — имя, число клубов, счётчики по статусам. Отдельным блоком — **фотоотчёт**
(ожидается / получен / просрочен) как самостоятельный контролируемый показатель.
Ниже — карточки кампаний с кольцом и разбивкой, раскрытие в таблицу размещений.

Таблица редактируемая: статус с раскрытием деталей, кто едет и ответственный,
статус фотоотчёта, отметка о выполнении задач.

| Статус размещения | Раскрытие |
| --- | --- |
| Не отправлено | не готов макет · ждём АП · нет бюджета · не назначен ответственный |
| Ждём ответ | от клуба · от менеджера · подтверждение даты · согласование макета · подтверждение размещения |
| Одобрено | согласовано полностью · согласовано с условиями · дата подтверждена |
| Отказ | клуб отказал · нет свободных мест · макет не согласован · перенесено |

## Пользователи и доступ

| Роль | Что может |
| --- | --- |
| `admin` | Всё, включая пользователей и настройки |
| `editor` | Статусы слотов и размещений |
| `viewer` | Только просмотр |

Права проверяются и в интерфейсе, и в базе через RLS (`lockers_is_admin()`,
`lockers_can_edit()`, `lockers_can_view()`).

Выдать доступ: Supabase → Authentication → Users → Add user (галочка Auto Confirm),
затем `/admin/settings` — назначить роль по той же почте.

## Демонстрационные данные

Статусы слотов и зеркал, закрытия с причинами, брони, пересечения, восемь
кампаний с размещениями и фотоотчётами. Всё выдуманное, кроме списка клубов.

Очистка:

```sql
delete from lockers_slot_status;
delete from lockers_placements;
delete from lockers_campaigns;
```

Клубы, сети, менеджеры и пользователи остаются — это боевые данные.
